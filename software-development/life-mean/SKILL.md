## Architecture truth (read before building anything)

- **The multi-agent core is already complete and reused**: EventBus, Message, SmartRouter (`core/assignment/router.py`), Worker, ToolWorker (`core/workers/tool.py`, 59 deterministic tools), tool detection (`library/tools/detection.py`), personas, reflection/stagnation protocols, reliability managers. DO NOT reimplement these — the generator hands tasks to them.
- **The sanctioned automated path is deterministic.** Use `ExperimentRunner` (`experiments/runner.py`) which drives `SmartRouter` + `ToolWorker`. `ExperimentUIController._run_experiment_loop` selects the runner by config: `debate=True` routes through `AutoPilot` (`experiments/autopilot.py`) → `DebateEngine` (the real multi-agent path), otherwise the deterministic `ExperimentRunner`. The design doc requires a deterministic factory by default, so keep the deterministic path the fallback; the debate path is opt-in via the `debate` flag (parsed as bool in `dashboard.py`). `AutoPilot._create_debate_engine` builds a REAL engine (real DB, real 6 agents, real moderator) with the DB keyed off `experiment_id` — tests should redirect that DB to tmp_path or `_create_debate_engine` will litter `experiments/{id}/debate.db` into the workspace.
- **Tool outputs are dicts, not raw values.** `ToolWorker` returns e.g. `{'valid': True, 'a': 13, 'b': 45, 'gcd': 1, 'lcm': 585}`. Extract the key named in the task description (`gcd`→result['gcd'], `lcm`→['lcm'], factorial→['factorial'], prime→['is_prime'], trig→['result']) BEFORE comparing to ground truth. `TaskGenerator` must only emit tasks that map onto a real tool signature.
- **Only math tasks actually execute.** `ExperimentRunner._execute_task` (runner.py) implements parameter extraction for math tool types (gcd, lcm, factorial, prime, fibonacci, trig) and nothing else. Physics/chemistry tasks DO get correct ground truth from the generator and DO route to the right tool (`physics_force`, `chemistry_molar_mass`), but the extraction builds empty `tool_kwargs`, so every task returns `no_answer` → 0% pass with no error shown. If you need non-math domains to work, extend the parameter extraction; until then, treat the deterministic pipeline as math-only and surface that limitation rather than expecting physics/chemistry to pass.
- **Code Lab (`code_lab/`) is the experimental code-generation layer** (V1, deterministic). It does NOT create a second engine — it orchestrates the stable core: `code_lab/engine.py` (CodeLabEngine pipeline: PLANNER → generator → real pytest in isolated workspace → compile()-based validation → RAW via RawDebateRecorder), `code_lab/workspace.py` (isolated `runs/<run_id>/` + security bounds), `code_lab/controller.py` + `generator.py` (deterministic Python templates). Wired into `experiments/dashboard.py` under `/api/code-lab/*` and a `dashboard.html` tab. Docs: `CODE_LAB.md`.
- **JudgeAgent genuinely does NOT exist in the used code path.** There is a `hermes-debate/agents/judge.py` but its module won't import — treat LLM-judge as ABSENT. `DebateEngine` (philosophical_council) is complete but requires LM Studio (`localhost:1234`, down in this env). A feature that needs a judge/LLM must either branch on `llm_available` or report judge_validation as "unavailable" honestly — never fabricate a Judge verdict to make a pipeline pass. When Code Lab DOES run an LLM semantic judge (multi-agent mode), that component is explicitly `code_lab.multiagent.SemanticCodeJudge` — it is NOT the hermes-debate JudgeAgent and must be named as such. Store `validation.deterministic_validation` (authority) and `semantic_judge` (opinion) under separate keys; a disagreement must never flip the deterministic result (rule 6).
- **Role Template system (`role_templates/`) CONFIGURES the stable core; it never replaces it.** `role_templates/` (experimental layer) holds `RoleTemplate` / `RoleSpec` / `RoleModelMapping` (role_id→model) + `RoleTemplateRegistry` + built-ins `coding-standard`, `philosophical-debate`, `general-reasoning`. Exposed via `GET /api/role-templates` and a Code Lab tab picker (per-role model dropdowns, blank = dynamic). Regression: `tests/test_role_templates.py` (spec tests 15.A–K).
- **`CodeLabConfig.role_models` is where per-coding-role models live, NOT `Config`/`ModelConfig`.** The stable-core `ModelConfig` only has debate-school fields (`existentialist`...`moderator`), so `get_model('planner')` returns `""` → always dynamic routing. ## Subject tree / folder architecture (`compare/subjects.py`) — compare by topic
- **Compare can be organized by a subject/topic folder tree, not only by id.** `SubjectTree` writes REAL folders under `data/subjects/<topic>/[<subfolder>/]`, each leaf holding one `*.exp.json` marker per experiment. A NEW topic auto-creates its general folder on first `register` — no manual mkdir.
- **Folder components are a security boundary `_safe_component()`**: rejects `/`, `\`, `..`, `.`, and shell-metacharacters (`:"*?<>|`) so a UI-provided subject can never escape the tree root (path traversal).
- **Minimal architecture from the actual RAW data (`bootstrap_from_raw`)** (topic = condition `domain`, subfolder = `difficulty_range`, the one variable that varies — the correlation axis). Runs with `num_tasks==0` no-verdict empty test artifacts are SKIPPED (47 of 147 raw runs; 100 registered; `math/other` when difficulty_range missing).
- **API** (CompareApiMixin): `GET /api/compare/tree`, `POST /api/compare/tree/register {experiment_id, subject}` (requires RAW evidence → 404 otherwise), `POST /api/compare/tree/bootstrap`, `POST /api/compare/subject {subject}` (compares ALL experiments under a path recursively — correlation view). Errors → 400 `invalid_subject`.
- **UI**: Compare tab has Bootstrap button, register input (exp id + subject), and a renderable folder tree; clicking a folder runs the subject comparison.
- **Pitfall**: never `register` a subject whose experiment has no RAW (marker pointing at nothing) — the API validates first. Tests: `tests/test_compare_subjects.py` (tmp roots only). `data/subjects/` is git-ignored.
- **`SubjectTree._walk` must guard a missing root (`if not base.is_dir(): return node`) before `os.listdir`** — the tree root can legitimately not exist (fresh/empty volume), and without the guard the whole `/api/compare/tree` endpoint 500s with `FileNotFoundError`.

## Dashboard Docker data sync (host `data/` → named volume)
- **The dashboard container NEVER sees the host `data/` directory.** `docker-compose.yml` mounts `life_mean_data:/app/data` — a Docker-managed NAMED volume, deliberately (the file comment says "No host bind mounts... not C: paths"; rootfs is `read_only`, `cap_drop ALL`, `no-new-privileges`). So host `data/subjects/` (tree markers) and `data/raw_debates/` (RAW .jsonl) are invisible to the Compare tab → empty tree crash + zero indexed experiments, even though `run_compare.bat`/`compare_mia.py` on the host sees all 335 experiments.
- **`docker cp` INTO a named volume works even with `read_only: true` rootfs** (the volume is writable): `docker cp data/subjects/. <container>:/app/data/subjects/` and same for `raw_debates`, then `GET /api/compare/browser?refresh=true` to rebuild `compare_index.json` from the copied RAW.
- **Do NOT "fix" this with a bind-mount** (`./data:/app/data`) — it silently breaks the container's isolation design (direct permanent read/write access to `C:` paths, contradicting the user's permission/isolated-execution rules). The sanctioned pattern is `sync_dashboard_data.py` (repo root): checks the container is running, `docker cp`s `subjects` + `raw_debates` into the volume, then triggers the index rebuild; reads `LIFE_MEAN_PORT` for the custom-port case. Wired into `run_server.bat` as step `[1.5/3]` (non-fatal warning if it fails) so every dashboard launch gets fresh host data. This is a one-way host→volume copy, never volume→host.
- **The Compare tab's two data layers are fed by two different folders**: `data/subjects/` (small `*.exp.json` markers → the tree/"📁 Subjects" hierarchy, `compare/subjects.py`) vs `data/raw_debates/` (heavy `.jsonl` evidence → the index/browser list with tasks/pass%/timestamps, `compare/index.py`). Both must be copied or the tab is half-empty — tree without list or list without tree.

## Compare V1 (`compare/`) — deterministic comparison of historical runs
- **The Compare index must include Code Lab AND Debate Lab runs, not only `data/raw_debates/*.jsonl`.** Their RAW snapshots live at `code_lab_runs/<id>/raw/run_<id>.json` and `debate_lab_runs/<id>/raw/run_<id>.json`; `compare/lab_runs.py` normalizes both into the SAME index-row shape (`source: code_lab|debate_lab`, `subject` = role template / project / debate topic, `num_tasks` = iterations or turns, PASS→COMPLETED) and into `RunMetrics` with **no task records** (`tasks=[]`; condition carries project/execution_mode/role_template/settings_snapshot, or topic/template_id/max_turns). `build_index` appends those rows and tags native rows `source: experiment`; the cache becomes stale when a lab snapshot is newer (`lab_runs_newest_mtime`). `load_experiment` / `list_available_experiments` delegate on the `codelab_` / `debatelab_` prefix, so inspect (`GET /api/compare/run/<id>`) and the pairwise engine work without a false 404. **Test isolation:** when `raw_dir` is passed explicitly (tmp fixtures), lab runs are EXCLUDED unless `include_lab_runs=True` — otherwise every real project run leaks into isolated scans and count assertions break. `bootstrap_from_raw` skips lab runs (no domain/difficulty) so 600+ runs don't flood `unknown/other`. UI renders `CODE LAB` / `DEBATE LAB` badges and `iterations` / `turns` units instead of `tasks`.
- **Compare reads RAW evidence, never writes it.** `compare/loader.py` reads `data/raw_debates/<experiment_id>.jsonl` (append-only RAW, one JSON object per task) and reduces each line into a `TaskRecord`, then `aggregate()` into `RunMetrics` (num_tasks/passed/failed/no_verdict, success_rate, by_domain/by_difficulty, tools/workers used, failure_reasons). A line with NO validation verdict is `num_no_verdict` — NOT_REACHED != FAIL is honored (never fabricated). Corrupt lines are skipped, never fabricated.
- **`compare/comparability.py` classifies pairwise comparability** from the immutable condition snapshot (NOT from outcomes): HIGHLY_CONTROLLED (identical conditions, or same domain + exactly 1 variable differs), PARTIALLY_CONTROLLED (same domain, 2+ differ), EXPLORATORY (different domain), NOT_DIRECTLY_COMPARABLE (self-compare / too different). **Honesty guard `_substance()`**: a minimal/legacy condition that only records `domain` is EXPLORATORY, never HIGHLY_CONTROLLED — two runs whose only recorded var matches must not be called controlled.
- **`compare/analyzer.py` separates findings** (spec §26): OBSERVATION (measured fact), HYPOTHESIS (interpretation — ONLY emitted when comparability is HIGHLY_CONTROLLED/PARTIALLY_CONTROLLED; an EXPLORATORY diff gets a bare observation + "do NOT interpret causally"), REPAIR_CANDIDATE (a tool appearing on failing tasks). Identical-conditions-but-different-rate → hypothesis about seed/stochastic variance, not a variable effect. `_failure_patterns` aggregates a failure reason appearing in >1 run.
- **API**: `compare/api.py` `CompareApiMixin` (dashboard inherits it) — `GET /api/compare/available`, `GET /api/compare/run/<id>`, `POST /api/compare {experiment_ids:[...]}`. Missing experiment → 404 (honest, never a silently reduced comparison). Dashboard has a Compare tab (`panel-compare`).
- **Wheel**: `compare*` and `experimental*` were MISSING from `[tool.setuptools.packages.find] include` — added both so they ship in the wheel.
- **Pitfall**: `PairOutcome` is an unhashable dataclass — never use it as a dict key; key pair findings by `(left, right)` ids. Tests: `tests/test_compare.py` (19 tests, isolated tmp RAW fixtures — never touch real `data/raw_debates`).

## Life_mean Studio (`life_mean_studio/`) — PySide6 launcher + health checks
- **`StudioStorage.connect()` must reuse the open connection** (`if self._conn is not None: return self._conn`). The original re-opened `sqlite3.connect()` on EVERY call, overwriting `self._conn` and leaking every earlier handle — on Windows a second handle on the same `.db` file holds a lock, so the file can't be deleted (`PermissionError [WinError 32]` at tempdir cleanup) and concurrent opens raise `sqlite3.OperationalError: database is locked`. This is the same root cause behind the widget-test "database is locked" teardown errors. `close()` resets `_conn=None` so a later `connect()` reopens.
- **`datetime.utcnow()` is deprecated and still called in Studio `engine/__init__.py` `StudioEvent` defaults** (`field(default_factory=datetime.utcnow)`) — same DeprecationWarning family as the `data/schemas`/`data/storage` targets; fix with `datetime.now(timezone.utc)` when that pass runs.
- **Studio health checks must probe the HOST-reachable URL, not the Docker alias.** Credentials precedence is `overrides/llm.env` BEFORE `.env` (Settings override > legacy .env). The root `.env` may hold `host.docker.internal` (the alias the CONTAINER needs) while `overrides/llm.env` holds `localhost` (what the host needs) — so read overrides first, and in `check_llm_backend` probe `localhost` first then fall back to the configured URL verbatim. Dashboard answers on `/dashboard`, not on the root — probe both.
- **Health check module lives at `life_mean_studio/engine/health.py`** (stdlib-only, testable without Qt): `run_all_health_checks(storage)` → storage/LLM/dashboard/orchestrator, each a `ServiceHealth` with status ok/degraded/error + latency. Tests in `life_mean_studio/tests/test_health.py` stand up a fake `HTTPServer` per service and monkeypatch `_load_llm_credentials`.
- **Fake-HTTP tests must reset the handler's class-level `behavior` attribute inside EVERY test.** A shared class attr (e.g. `behavior="notfound"`) set by an alphabetically-earlier test leaks into a later one — pytest orders by name, so `test_notfound` ran before `test_ok` and poisoned it. Set `Handler.behavior = ...` at the top of each test.
- **UI auto-probes must be gated on `_in_pytest()` (`"PYTEST_CURRENT_TEST" in os.environ`)** — otherwise the Services-page auto health check and model-combo loader fire real network probes during widget tests (100s suite → 0.4s). The Refresh button stays active; only the auto-triggers skip under pytest.
- **The PySide6 interpreter is `.venv/Scripts/python.exe`, NOT the system python and NOT `.venv.bakop` — `.venv.bakop` has been DELETED.** Run Studio tests with `.venv` (user correction): `python -m pytest life_mean_studio/tests/`. Widget/launcher tests error with `ModuleNotFoundError: PySide6` under system python — that's the wrong interpreter, not a test failure. A launcher `.bat` that still references `.venv.bakop/Scripts/python.exe` (`start_studio.bat`) fails SILENTLY — the missing exe means `python` never runs and no UI appears, with no error dialog. After any venv migration, grep the launcher `.bat`s for the old venv path and repoint them to `.venv`; verify with `ls .venv/Scripts/python*.exe`.

## Zero-secrets / packaging truths
- **Never hardcode an LM Studio token in source.** `philosophical_council/config.py` (both `DEFAULT_CONFIG["lm_studio"]["api_key"]` and the `LMStudioConfig.api_key` dataclass field) and `experiments/autopilot.py` (the old inline `LLMClient(api_key=...)`) had committed `sk-lm-...` keys — all purged to `""`. Credentials come ONLY from `.env` (git-ignored), loaded at import in `code_lab/config.py` via the minimal `_load_dotenv()` (no third-party dep, sets only unset env vars). `resolve_llm_credentials()` in `code_lab/multiagent.py` is the single resolution point.
- **`config.json` is ALSO loaded at runtime and can carry a key**: purge `philosophical_council/config.json`'s `lm_studio.api_key` too — a second, different key lived there.
- **Raw debate data can contain a leaked 401-error echo** (`storage/raw_data/*.json` `agent_calls[].output_received` / `debate_events[].content`, `storage/debates/debate_log_*.txt`, runtime `philosophical_council/debate.db` `turns.response`): LM Studio's 401 body replays `sk-lm-...` in the error message. Historical RAW is IMMUTABLE per the raw-data rule — never rewrite it. The DURABLE fix is a redaction guard at the single persistence point: `raw_protocol.redact_secrets()` is applied to `input_sent`/`output_received` in `record_agent_call` and `content` in `record_debate_event`, stripping `sk-*`, `ghp_*`, `gho_*`, `github_pat_*`, and email-like credential patterns so no future RAW or debate DB can persist a credential again (regression `tests/test_raw_secret_redaction.py`).
- **The runtime `debate.db` is a generated SQLite (NOT immutable RAW) and must not be git-tracked.** `DebateEngine` regenerates `philosophical_council/debate.db` per run (`db_path` default) and its `turns.response` echoed the token. ## Context-State Audit Methodology (Evidence-Based, Read-Only)

When auditing Life_mean's architecture for context handling, compression, or state flow:

**STRICT DEFINITIONS (do not conflate):**
1. `DETERMINISTIC_EXECUTION` = task/tool/validator executes by rules (`execution_mode="deterministic"`). Does NOT imply structured context or compression.
2. `CANONICAL_CONTEXT_STATE` = compact structured representation fed to LLMs (fields: goal, validated_facts, observations, hypotheses, open_questions, constraints, failures, source_refs, state_version). Often DOES NOT EXIST.
3. `LLM_CONTEXT_COMPRESSION` = LLM summarizes large context into smaller form (e.g., Hermes aux model). Only in `legacy/` — NOT active Life_mean.
4. `FULL_HISTORY_BEHAVIOR` = what the LLM receives. Trace actual message construction, not just grep for `FULL_HISTORY` symbol.

**TRACE ONE REAL PATH:**
```
USER INPUT → Controller → Agent → Prompt construction → History retrieval → LLMClient → messages payload
```
Classify every component: CONFIRMED_SOURCE / INFERRED_STATIC / UNKNOWN.

- FULL_ACCUMULATION = list append, no removal, no token limit
- WINDOWED_HISTORY = fixed-size window (recent N turns)
- SUMMARY_REPLACEMENT = old messages replaced by LLM summary
- STRUCTURED_STATE = compact object fed to LLM (rare/nonexistent in Life_mean)

- IS IT COMPACT? VALIDATED?

## Cluster Graph CG1 (`compare/graph.py`) — deterministic future Tree/Graph model
- **`build_graph(rows, subjects, conditions=None, thresholds=, version=, algorithm=)` returns a `ClusterGraph`** (nodes `run:<eid>` / `subject:<top-topic>`, edges, connected-component clusters). Consumes existing data only: index rows (`compare/index` shape: experiment_id, domain, seed, tools, workers, ...) + a real `SubjectTree` + optional per-run CONDITION dicts for comparability. Deterministic, no LLM, no RAW writes.
- **Three separate edge categories, non-interchangeable**: `belongs_to` (RUN→top-level SUBJECT node, `subject_membership`, no score; a nested subject points at its TOP-LEVEL topic node to avoid dangling targets — the full path rides in `meta.subject`), `similarity` (run↔run `jaccard_tools` / `jaccard_workers` and subject↔subject `jaccard_run_overlap`, numeric rounded score, only when score >= `similarity_threshold`, default 0.2), `comparability` (run↔run, method `comparability_kind`, NO numeric score — REUSES `compare_pair` from `compare.comparability`; emitted ONLY for HIGHLY_CONTROLLED / PARTIALLY_CONTROLLED; the `ComparabilityKind` + `common/changed_variables` + `reason` ride in meta). NEVER convert ComparabilityKind into a similarity percentage.
- **Clustering**: union-find connected components over the similarity edges only; cluster id `cluster:<min-node-id>`; deterministic (everything sorted by node_id, no set-iteration order). IDs are namespaced (`run:`/`subject:`) so a run and a subject sharing a name never collide.
- **Cache**: `build_cached(...)` keys on `source_fingerprint` (SHA-256 over canonicalized annotations + subject membership + conditions — NOT mtimes) and `params_fingerprint` (version+algorithm+thresholds); `save_graph`/`load_graph` to a JSON file. Recompute iff a fingerprint changes; identical sources+params ALWAYS reuse. Prove non-rebuild by monkeypatching `graph.build_graph` with a call counter in tests.
- **PITFALL**: `_connected_components` sorts components with `sorted(comps)` (each comp is already a sorted list) — sorting by `(c[0], c[1])` breaks on SINGLETON components (IndexError).
- Tests: `tests/test_cluster_graph.py` (12) cover empty / isolated / dense / multi-subject+runs / id collision / determinism / provenance / comparability-vs-similarity separation / cache reuse+invalidation / 180-run volume.

## Pitfalls

- **A lockfile-guarded launcher `.bat` leaves a STALE lock after any interrupted run, silently blocking every later launch.** `run_server.bat` writes `.run_server.lock` up front and deletes it only on the normal `exit /b 0` path — kill the window, crash mid-run, or restart the machine and the lock survives forever, so the next run prints "already running" and exits 1 even though no instance exists. Before deleting a stale lock, verify no live process matches: `powershell -NoProfile -Command "Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'run_server\.bat' }"` (bare `tasklist //FI "IMAGENAME eq cmd.exe"` and `wmic` return nothing useful — target CommandLine). Better: write the PID into the lock and only treat it as live if that PID still exists, so stale locks stop being a recurring user-facing error.
- **An LLM "source" that is a bare markdown fence must be rejected as phantom DEVELOPER output, never written.** A DEVELOPER response like `"```"` passes `not src.strip()` (it's non-empty), so a fall-back-to-raw extractor writes the fence into a `.py` → `SyntaxError` at collection that the CRITIC/repair loop can NEVER fix (it can't parse the file to produce a patch). Guard the extraction: if fenced text did not yield a complete ```…``` block, treat it as degenerate (`src=""`) and only fall back to raw text for UNFENCED plain code. Factor extraction into ONE helper (e.g. `_developer_source(resp)`) so both attempts share it. **One degenerate draw is NOT a terminal verdict: give the DEVELOPER exactly one fresh retry first** (a second `ma.develop` call, which emits its own `AGENT_STARTED` and is recorded in `agent_trace` with `attempt=2`). Only when BOTH attempts are unusable surface `developer_stage_failed` (message "empty/phantom output after retry") → `det=NOT_REACHED`, no fence written. The degenerate first attempt must never have been written before the retry succeeds.
- **Never spawn a subprocess with the bare string `"python"` — use `sys.executable`.** CodeLab `_run_tests` did `subprocess.run(["python", "-m", "pytest", ...])`, which resolved `python` from PATH to the uv-managed `cpython-3.11` interpreter that has NO pytest installed, while `sys.executable` (the `.venv/Scripts/python.exe` running the engine) does. Every deterministic Code Lab run then failed at `pytest_iter1` with `No module named pytest` even though the generated source/tests and structural validation were correct. Any code that shells out to run the *same* toolchain must pass `sys.executable` so the subprocess uses the interpreter actually running the project, never one picked off PATH.
- **A package directory shadows a same-named `*.py` module.** Before creating a module like `experiments/failure_bank.py`, check whether `experiments/failure_bank/` (a package) already exists — if it does, your flat file is silently ignored on import and your code fails at runtime with confusing errors. Search the tree for the name first.
- **`python -m <module>` starting a server exits immediately and silently unless the module has `if __name__ == "__main__":`.** A long-running script (dashboard, watcher) launched via `-m` that returns instantly with empty output usually means the entry-point guard is missing — add it, don't chase the server.
- **Verify-on-disk before trusting a context summary or build list.** A handoff/compacted summary may report components as "missing" (e.g. FailureBank) when they were already implemented. Grep the file tree for the symbol/package and run the phase tests before writing something from scratch — avoids duplicating existing work. For "capture this spec in the roadmap" tasks, also check whether the target file already contains it: diff the extracted region against the attachment with a whitespace-normalized `difflib.SequenceMatcher` (collapse trailing spaces + blank-line runs) and accept a ratio of 1.0 as "already captured verbatim — do not re-append" rather than duplicating a byte-identical section.
- **Zombie servers keep a port busy on Windows.** To free a stuck port: `netstat -ano | findstr :8080 | findstr LISTEN` to find owning PIDs, then kill via PowerShell `Get-NetTCPConnection -LocalPort 8080 -State Listen | % { Stop-Process -Id $_.OwningProcess -Force }`. `pkill`/native `taskkill` from git-bash can miss or refuse; PowerShell is the reliable path.
- **git-bash `>` redirection into `/tmp` is invisible to native Windows tools.** `sed … > /tmp/x` writes to the MSYS `/tmp`, but a native Python process resolves `/tmp/x` as `C:\tmp\x` → `FileNotFoundError`. Note `$TMPDIR` in this git-bash ALSO expands to the MSYS `/tmp`, not the Hermes scratch dir. For a file a native tool must read (Python, node, git), write it with an explicit `C:/…` forward-slash path (e.g. `$LOCALAPPDATA/Temp` or the Hermes scratch dir) and pass that SAME path to the native tool.
- **Code Lab workspace tests must pass `base_dir=tmp_path` — never let `CodeLabWorkspace(cfg)` default to CWD.** Without base_dir it writes under `code_lab_runs/<run_id>/` in the working tree; a test that "passed alone" creates real RAW files there, and the next run of the SAME test fails in a batch because `write_raw_snapshot` refuses to overwrite ("RAW snapshot already exists — immutable"). Constructor and controller both take `base_dir` — pass the same `Path(tmp_path)` to both.
- **Live-LLM integration tests contend with ANY other process hitting the same LM Studio backend.** Running the full suite in the background while a browser E2E (or another test) issues real `chat/completions` to `localhost:1234` makes the backend busy/timed-out, so a live test's `execution_mode == "multi_agent"` assertion flips to deterministic and fails — even though it passes alone when the backend is idle. Sequence live-LLM E2E against full-suite runs; when a live test "fails in the suite but passes alone", re-run it solo with the backend idle before suspecting a regression.
- **Never force `scrollTop = scrollHeight` on every re-render of a polled panel — it makes the history unreadable.** The Code Lab / Debate Lab conversation and log panes rebuild their DOM on each poll (~1s); an unconditional jump-to-bottom snaps the view back the instant the user scrolls up, so they report "the slider keeps going back to the end and I can't read the reasoning". Capture the scroll state BEFORE replacing `innerHTML` (top/height/client) and restore after: auto-scroll only when the user was already within ~40px of the bottom, otherwise reinstate the old `scrollTop`. Helpers `_scrollState` / `_applyScrollState` / `_captureScrollById` / `_restoreScrollById` live right after `const API_BASE` in `dashboard.html`; apply them at every re-render site (5 today: `cl-conv-scroll`, both `.clab-log` logs, `dl-conv-scroll`, the harness `fb` panel). An explicit "Latest" button may still jump to bottom — that is user intent, not a poll.
- **A dataclass `to_dict()` that omits a field breaks the JS that reads it.** When a `run`/`experiment` view's `to_dict()` doesn't serialize `config` but the frontend does `r.config.prompt`, the list renders empty while the raw JSON fetch clearly returns data — and the console shows a non-fatal `Cannot read properties of undefined` only if you've registered an `error`/`unhandledrejection` listener. Symptom signature: page shows "No runs yet", `curl`/`fetch` shows N items, JS errors = 0 because the error is inside an `async` handler that swallows it. Fix: add the missing key to `to_dict()`, then force a browser reload (the browser caches the old HTML/JS; a plain `switchTab` re-call keeps showing stale state until you `location.reload()`).
- **A "phantom turn" guard must roll back the optimistic reservation, not just skip the completion.** An LLM-driven turn orchestrator often reserves a turn in argument/turn state BEFORE generating (`add_turn(response='')` bumps `turn_count`/`recent_speakers`/`speaker_turn_count` so the moderator can build context), then fills the real response after generation. If your empty-response guard only returns `False` before `complete_turn`, the reservation still pollutes the state and looks like a real turn. The guard must call a `rollback_reserved_turn(speaker)` that decrements exactly the three counters the reservation touched — otherwise a test asserting "turn_count unchanged after an empty response" still fails with `assert 0 == 1` sporadically.
- **A `BaseHTTPRequestHandler` subclass silently 501s any HTTP verb it doesn't name.** Adding `POST /api/settings` routes is not enough — the frontend `PUT`s updates, and without an explicit `do_PUT` method the server replies 501 (`{'error': 'Unsupported method'}`) while your tests (which hammer GET/POST) stay green. When you add a write route, define the ODD-verb handler (`do_PUT`) alongside `do_POST`, and test it with `curl -X PUT` (which is what the browser sends), not only with your test client.
- **A lifecycle/status field must live ON the dataclass, not in a controller-side dict, or `to_dict()` returns null.** Derived UI fields (status, mode) exposed through `ExperimentState.to_dict()` will come back null/missing if you store them in a separate `controller._mode` map and look them up via a `hasattr(self, "_mode")` heuristic — the state dataclass never sees the controller's attribute. Put the field on the state (`mode: str = "deterministic"`), set it in `register_experiment` from the config, and serialize it directly.
- **A "newest" selection keyed on a float timestamp must tie-break on registration order, or it flips with the run.** `ModelRegistry.get_by_name` did `max(matches, key=lambda m: m.created_at)`; `created_at` is `time.time()`, and two candidates registered in the same clock tick tie, so `max()` fell back to dict-iteration order and returned the FIRST, not the newest — flaky `test_get_by_name`. Any "pick the most recent" keyed on a float timestamp is tie-prone; resolve ties explicitly with the registration index: `max(enumerate(matches), key=lambda iv: (iv[1].created_at, iv[0]))[1]` (match list preserves insertion order). Same family as the Debate Lab rule — a deterministic selection must break ties explicitly, never leave them implicit to set/dict order.
- **A network probe in a worker thread needs an explicit timeout or the failure-path hangs forever instead of failing fast.** Gating `debate` mode on `probe_llm(...).get("available")` is the right no-silent-fallback pattern, but a probe that issues `LLMClient.get_models()` to a down/unreachable backend (e.g. `localhost:1234`) with `requests`' default (no) timeout blocks the experiment thread indefinitely — the UI shows STARTING/RUNNING forever rather than FAILED. Give every backend probe a short `timeout=` (2-5s); a fast, honest FAILED beats a hung RUNNING.
- **`LLMClient.get_models()` swallows the backend exception and returns `[]`**, so an invalid/401 LM Studio token (or an empty backend) is indistinguishable from "no models" — every model dropdown (Settings 'Models per role', the Code Lab Role-Template picker) renders blank with no explanation, and `probe_llm()` reports the generic `no_models_or_auth` rather than `invalid_api_token`. When the user reports "my LM Studio models don't show", diagnose the BACKEND FIRST (the server log shows `401 Invalid LM Studio API token: sk-...`) before touching the UI — the app is being honest; the `.env`/override token is stale. Then surface the reason instead of a blank list: map probe codes to actionable messages (`no_models_or_auth` → 'token rejected or no model loaded') and expose `inference.llm_error` / `inference.models_available` on `GET /api/settings` and in the Settings JS.
- **A backend probe inside a GET handler must run in a daemon thread with a short `join` — the dashboard `HTTPServer` is single-threaded.** A request-scoped probe (the Settings view calls the backend on every load) that blocks on a hanging/dead backend would freeze EVERY request on the whole dashboard, not just its own path. Wrap the probe as `t = threading.Thread(target=_run, daemon=True); t.start(); t.join(4.0); if t.is_alive(): error = "backend_unreachable (probe timed out)"` so a dead backend degrades to a surfaced error instead of hanging the server. This is the GET-handler analogue of the worker-thread probe-timeout rule above.
- **A Grade/Debate-mode fail should be an explicit state transition, not an unobserved thread exception.** If the guard `raise RuntimeError(...)` inside the worker is caught by the broad `except` and only `add_error` is called, the state settles on FAILED — good — but make sure the lifecycle derivation marks it FAILED (has errors, not running). Derive status from real state so a failed experiment shows FAILED, and never run deterministic silently under a Debate label.
- **`AutoPilot._create_debate_engine` accepts injection**: signature `(experiment_id, config, llm_client=None, db_path=None)`. Pass a deterministic stub as `llm_client` and a tmp `db_path` in tests → NO real `LLMClient` is constructed (no network), and no `experiments/<id>/debate.db` is littered. This is the Goal-3-correct way to test the engine; build + replace after construction is the anti-pattern. The same apply-injection-before-construction principle governs `CodingMultiAgent`: accept `llm_client=<stub>` and only build a real `LLMClient` when none is supplied, so unit/deterministic tests never touch the network or need an API key (live integration tests pass a real client).
- **`openai.OpenAI(...)` enforces a non-empty `api_key` AT CONSTRUCTION** — `OpenAI(base_url=..., api_key="")` raises, so any unit test that builds a real `LLMClient` (whose `__init__` instantiates OpenAI) fails even with no network/token involved. Never construct a production client in a unit test just to reach the layer above it: inject the stub into the collaborator (`CodingMultiAgent(llm_client=_StubLLM())`) so `__init__` never builds OpenAI. Tests cover the layer, not the network handshake.
- **A patch that trims a line ending in a CSS/HTML block comment can glue the comment onto the next selector** (`*/        .clab-grid {`) — still valid CSS but the rule is fused to the comment. When patching multi-line CSS, keep the block-comment terminator on its own line and re-check the rendered pane; a `lint: skipped` on `.html` gives you no safety net.
- **`_run_task_through_debate` was flaky because it validated `all_turns[-1].response`** — a real debate ends with a reserved/rejected turn (moderator repetition guard) whose response is empty, so `is_valid` flips False ~50% in full suites though it passed alone. Fix (in `experiments/autopilot.py`): walk `reversed(all_turns)` and take the FIRST non-empty `(t.response or "").strip()` as `final_response`. Validate real content, never a phantom trailing turn. Repro at scale (8 loops) before/after confirms the flake disappears.
- **A genuine DebateEngine integration test stubs the LLM layer, NOT the engine.** To prove an orchestrator actually works (rule: tests are evidence, not mocks), instantiate the REAL `DebateEngine`, real sqlite `Database` (point it at tmp_path), real TurnManager, real argument_state, and register the REAL philosophical agents+moderator. Replace ONLY the `chat()` backend with a deterministic stub that returns (a) valid moderator JSON for temperature==0.5 (the moderator's temp) and (b) an answer for agent temps — the moderation JSON must ROTATE speakers, else the real repetition guard kicks in and the debate falls to the deterministic fallback (flaky `step_once`). Assert against real mutated state: turn_count grew, a turn with the answer is persisted, agent history mutated. Never `MagicMock`-the-whole-engine "integration" test — and never write `assert x is not None or True` (a tautology that can never fail; `or True` makes any assertion vacuous).
- **A stale/placeholder `.env` key or a flapping backend makes LLM-gated tests flaky.** `probe_llm()` is evaluated once at module import for `@pytest.mark.skipif(not has_llm)`; if the LM Studio backend is up during collection but down at runtime (or the `.env` holds a placeholder like `REMPLACE_MOI_PAR_LE_TOKEN`), the live tests run against a dead backend and FAIL instead of skipping. Keep the gating decisive: either the credential is genuinely valid or the test skips — a placeholder token is NOT "available". When a LLM test fails only in full-suite runs but passes alone, suspect the backend flapping, not your code.
- **An unknown form field must be filtered, never forwarded into `ExperimentConfig(**data)`.** The dashboard sent a stray `_deterministic_force` checkbox value the config doesn't accept → `TypeError` → caught by the broad `except Exception` → opaque 500 "Failed to create experiment" in the browser and an honest backend misread as a crash. Before constructing the config, whitelist to the dataclass fields: `known = {f.name for f in dataclasses.fields(ExperimentConfig)}; data = {k: v for k, v in data.items() if k in known}`. Keep the mapping of UI conveniences to backing flags (`mode` → `deterministic`/`debate`) in the route handler so the selector stays the single source of truth, and remove a redundant checkbox that forwarded a SUPPRESSED duplicate of the flag (two controls for one decision = a second, unbound source of truth). The hardened form of this is one helper, `_validate_experiment_input(data)` in `experiments/dashboard.py`: iterate a WHITELIST of keys (never the request's keys), coerce `num_tasks`/`seed` with `int()` inside `try/except` → `ValueError` with a human message, coerce booleans from `"true"/"1"/"on"`, parse `difficulty_range` from a JSON string or list into a 2-tuple, and map `mode` to flags; then merge only keys that are real `ExperimentConfig` fields. `_create_experiment` becomes a thin wrapper: validate → construct → register → return `{"experiment_id", "status"}`. Secrets stay server-side (the LLM key is read inside the handler, never echoed), and the broad `except Exception` returns a generic `500 "Failed to create experiment"` — no traceback, path, or config value ever reaches the browser.
- **A free-form ("generic") Code Lab task must never be validated against an invented single-function oracle.** The old `generic` plan wrote `test_main.py` with `from main import run; assert isinstance(run(), str)`, which rejects valid arbitrary projects (Tetris, GUI, libraries, multi-file) → FALSE FAILURES and doomed CRITIC-repair loops against an unrelated test. Free-form tasks (`plan_id == "generic"`) skip the oracle test entirely and run truthful structural validation instead: compile/parse every generated `.py` + expected-files-present, with explicit levels (`syntax_validation` / `generated_tests: NOT_AVAILABLE` / `task_semantic_validation: NOT_AVAILABLE`) and a `validator_protocol` (`code-lab-v2-freeform` vs `code-lab-v2-known`) so old and new runs stay distinguishable (RAW immutable). Known templates (fibonacci/factorial/is_prime/…) keep their strong oracle — never downgrade them. Add `is_freeform = generated["plan_id"] == "generic"` in `_execute`, branch before the verify loop, and honor `stop_requested` in that branch. Coding Pool (Settings): per-code-role models (planner/developer/critic/reviewer/judge) live in Settings overrides `coding_pool` and are inherited into `CodeLabConfig.role_models` in `dashboard._code_lab_create`; agent events record `configured_model` (null when unset) + `selection_mode` (`configured`/`dynamic`/`backend_default`) + actual model — never present an empty configured model as a selection. Settings exposes ONE unified per-domain accessor `experiments.settings.model_pools()` → `{"coding": {...}, "debate": {...}, "sandbox": {}}` (sandbox reserved/future, empty); coding and debate read the same layer, and any new pool goes behind a domain key there — not a new ad-hoc setting. `dashboard._code_lab_create` inherits the pool into `role_models` when the request omits it.
- **When surgical `patch` edits keep corrupting a large nested block, STOP re-patching and re-read the exact on-disk lines.** A fuzzy-match `patch` over a big region (multi-function test bodies, class blocks) can silently duplicate, nest, and even inject literal markup into the target until lint reports an `IndentationError` you did not write. Each further ``patch`` compounds the mess. Recovery: `read_file` the exact region, then replace it with ONE clean anchored patch whose `old_string` is copied verbatim from that read — or rewrite the whole file once symptom-free when the region spans most of it. Never pinch more than one edit per multi-function block in a fuzzy match. And do not paste the replacement body into chat before running it — when the user has already authorized a patch, call the tool (or `write_file`) in the same turn; printing the diff first burns tokens, invites interruptions, and repeatedly loses the turn before anything lands on disk. The most reliable bypass: a tiny Python sanitize script (run via `execute_code` or `python -c`) doing exact-string read→replace with `assert src.count(old) == 1` per edit and `py_compile.compile(path, doraise=True)` before writing back — exact-match replaces CANNOT re-nest indentation the way the fuzzy `patch` tool does, and the `assert count==1` turns a bad anchor (0 or 2+ matches) into an explicit stop instead of a silent corrupted file. Test-after-each check is the delta-vs-fuzzy-match win for multi-edit Python refactors.
- **Never `str.strip(suffix)` to remove a URL suffix — it strips a CHARACTER SET from both ends.** In the sandbox HTTP routes, extracting a design_id with `parsed.path.strip("/run")` silently removed the leading `/` (and would strip any `r`/`n`/`u` hex chars from the id), so the id never matched the `^/api/.../([^/]+)$` regex and the endpoint returned 404. Use strict slicing `path[:-len(suffix)]` then `.split("/")[-1]` (or a precise regex) — verify with a live-HTTP test, not just the handler-level one.

## Credentials, providers, settings overrides & new dashboard tabs
- **The runtime reads `LIFE_MEAN_LLM_BASE_URL` + `LIFE_MEAN_LLM_API_KEY` ONLY** (`experiments/credentials.py` `ENV_BASE_URL`/`ENV_API_KEY`). `OPENROUTER_API_KEY` is NOT consumed by the LLM path until a provider selector wires it. Credential precedence is process env > `overrides/llm.env` > `.env` — the override file SHADOWS `.env`, so editing `.env` alone is often a no-op. All runtime LLM paths resolve through the SINGLE function `credentials.resolve_llm_credentials()` (callers route via `code_lab.multiagent.resolve_llm_credentials`, which delegates to it) — route any provider switch there, nowhere else.
- **Adding a new runtime override field (e.g. a `provider` selector) needs THREE touches**: (1) a special case in `settings.update_settings` placed BEFORE the `err = _validate(key, value)` fallback (a key not in `_EDITABLE` is otherwise rejected as `unknown setting`), persisting to `overrides/settings.json`; (2) expose it + its options in `get_settings()`; (3) consume it in the single credential resolver. To read the override file from a non-settings module, mirror `experiments.settings._overrides_path()` (LIFE_MEAN_OVERRIDES_FILE env or `overrides/settings.json`).
- **To list TWO backends' model pools side by side (LM Studio + OpenRouter), probe each provider independently** — never route both through the single active-provider `resolve_llm_credentials()` (it returns ONE pair). Resolve each provider's creds explicitly and call `_backend_models()` per provider; a missing key should short-circuit that provider to `no_api_key` WITHOUT a network probe, so one down/empty backend never blocks the other (OpenRouter's `/models` is public — returns ~470 models even with a placeholder key; LM Studio on localhost refuses fast when down).
- **Adding a new dashboard tab = FOUR edit points, then validate**: (1) nav `<button>` (`onclick="switchTab('<name>', this)"`), (2) a `switchTab` case (`if (name === '<name>') loadX();` — a missing case keeps the tab blank silently), (3) a `<div id="panel-<name>" class="tab-panel">`, (4) the JS loader/render fns — then `node --check` the extracted `<script>` block. A tab can be fully client-side by reusing existing endpoints (e.g. `/api/compare/tree` + a run listing), avoiding a new backend route.
- **`/api/code-lab/runs` and `/api/debate/runs` are IN-MEMORY session run lists (`Controller._runs`), NOT disk directory listings** — they show only the current process's runs. A run-DIRECTORY explorer (e.g. a "Cluster Tree" tab listing `code_lab_runs/` / `debate_lab_runs/`) needs its own endpoint that `os.walk`s those dirs (keep it bounded — cap entries, truncate with a marker).
- **History-rewrite / secret purge (git filter-repo, force-push, resync)**: `git grep --cached` scans the WHOLE index not just staged files; full-history scans use `git rev-list --all` loop; a rewrite removes `origin` and changes all SHAs. Full procedure in `references/history-rewrite-secret-purge.md`.

## Experimental (`experimental/`) — sandbox that COMPOSES the existing core, never a new engine
- **`experimental/` is the Experimental Engine + Designer package.** `schema.py`: versioned `ExperimentDesign` + `DesignAgent`/`DesignStage`/`DesignBudgets`, lifecycle DRAFT→REVIEWED→APPROVED→FROZEN (REJECTED/SUPERSEDED), science-only `content_hash()` (excludes status/ids/timestamps, INCLUDES version). `dispatch.py`: `STAGE_EXECUTORS` maps a stage's `executor_type` to the compatible EXISTING component — code_lab→CodeLabEngine (connected), debate→DebateEngine, research→ResearchWorker, general_reasoning, review, synthesis (all NOT-connected → `EXECUTOR_NOT_AVAILABLE`, no fake fallback). `validation.py`: DETERMINISTIC-FIRST structural checks; `require_executable` only lets a FROZEN+valid design run. `designer.py`: `ExperimentDesigner.propose()` returns a DRAFT-only team with layered system prompts; the 0.6B `EXPERIMENT_DESIGNER` role is interface-only/probe-gated, never hardcoded. `engine.py`: `ExperimentalEngine` facade — freeze gate + per-stage dispatch + truthful EventBus events (`EXPERIMENT_STARTED/STAGE_*/EXPERIMENT_COMPLETED|FAILED|STOPPED`); human STOP → STOPPED not FAILED; an unbound-but-connected stage reports `not_bound` instead of faking. `prompts.py`: 7-layer composition + prompt/component hashes. **Invariants to preserve**: the LLM may PROPOSE but never silently START or mutate a frozen design; the dispatcher keeps CodeLabEngine coding-only; heavy executors are INJECTED (`executors={kind: callable}`) — the engine only routes. Tests: `tests/test_experimental_engine.py` (spec §22 items 1-8, 12, 13).
- **Wiring (committed):** `experimental/executors.py` adapters — `code_lab_adapter` builds `CodeLabConfig(prompt=stage.request or research_question, template_id, multi_agent=False unless stage asks, deterministic_validation=True)` and calls `CodeLabEngine(config).run()`; `tool_adapter` calls the SYNCHRONOUS `core.workers.tool._execute_tool(name, **kwargs)` (directly, not via the bus) for deterministic/tool stages; `build_engine()` pre-binds kinds `code`->code_lab_adapter, `deterministic`->tool_adapter. `experimental/store.py` (`ExperimentDesignStore`, id->design, transition only). `experimental/api.py` `ExperimentalApiMixin` (dashboard inherits it) implements `/api/experimental/capabilities | /designs | /designs/{id} | /designs | /designs/{id}/transition | /designs/{id}/run`. Run ONLY when FROZEN: DRAFT->400 DESIGN_INVALID, unconnected stage->422 EXECUTOR_NOT_AVAILABLE, human stop->200 STOPPED. `_send_json` takes NO status kwarg (always 200). Real path verified offline: gcd(12,8) -> ToolWorker -> COMPLETED.
- **Experimental harness (`experimental/harness.py` + `POST /api/experimental/harness` + an `Experimental` dashboard tab): OPT-IN, additive surface whose WHOLE contract is that the stable core does NOT depend on it.** The harness reaches INTO the core (CodeLabEngine / ToolWorker) to run ONE executor (`run_executor(executor_type, payload)`) isolated in a throwaway `tempfile` root (cleaned in `finally`), so no `code_lab_runs/<id>` workspace is ever created in the project and nothing is registered/persisted. Only `connected == True` executors run here; a `not-connected` executor (debate/research/synthesis/review/hermes_debate) is refused with `EXECUTOR_NOT_AVAILABLE` (422) and an explicit message — never faked, never silently skipped. The dashboard's existing tabs/JS stay untouched (legacy); the only edits are additive: one nav `<button>`, one `switchTab` line, one `panel-experimental` block, and the harness JS. User's standing rule (restate when promoting to core): keep the stable core independent of any experimental UI; promote an executor to the core only after it proves value in the sandbox. The capabilities endpoint drives the tab's executor dropdown/table (`connected` vs `reserved` label). Tests: `tests/test_experimental_harness.py`.
- **`debate_code` executor (in `experimental/`, kind `debate_code`): a closed DEBATE→DECISION_SPEC→CODE→VERIFY chain with TWO modes sharing ONE generic spec→code compiler.** MODE A (default `deterministic`): a catalogue (`CATALOG`) of task types (`retry_controller`, `alert_routing`, `payment_gate`), each with its own fixed role debate (Architect/Reliability Engineer/Skeptic/Simplicity Advocate + Moderator), fixed DECISION_SPEC, generated pure-Python decision module + deterministic pytest tests, verified in a throwaway real-pytest workspace. `run_debate_code(task_type=, seed=, mode=, task_prompt=)` returns the full inspectable trace `{debate, handoff, code_files, verify, status, reproducible}` with a `spec_hash` (SHA-256 over machine-relevant spec fields only). The generic compiler turns ANY validated spec into `Action` str-enum + module-level constants + a pure `func(state)` implementing `decision_rules_priority` first-match-wins verbatim; `compile_tests` derives the default-action expectation from the spec's terminal else/empty-if rule, NEVER from `allowed[0]` (that mismatch failed `alert_routing` — its default is `LOG_ONLY`, not the first output). MODE B (`mode='llm'`): an LLM runs the debate and returns a DECISION_SPEC JSON that goes through the SAME validator before compiling.
- **PITFALL — a large run of a deterministic chain with unchanged input is a TAUTOLOGY, not a stress test.** Running `debate_code` 100× on the same task_type+prompt re-derives the identical chain and proves only stability, giving false confidence. To make N-runs meaningful, VARY the content (round-robin `task_type` × `seed`) AND assert two things in the matrix: spec hashes are DISTINCT across task types (the content really differs) and STABLE per type across seeds (no hidden global state leaked in — a changing hash across seeds means a global counter/clock influenced the spec). A sweep whose only lesson is "100/100 PASS" with nothing varied has not tested the system. `experimental/sweep.py --runs N --all` automates this (evidence: 90 runs × 3 types = 90/90 PASS, 3 distinct hashes, 1 per type). **`sweep` is itself a CONNECTED harness executor** (registered in `dispatch.STAGE_EXECUTORS` with `kind='sweep'`, runner `_run_sweep` in `harness.py` that calls `sweep.sweep(runs, types)` and returns a `passed/failed` status + `{status_counts, matrix, failures, total_duration_s, all_green}`) — so it appears automatically in the Experimental tab's executor dropdown/table (list built from `/api/experimental/capabilities`, no front-end edit needed to surface a new executor). UI limitation: the tab sends only `{executor, prompt}` (no `runs` field), so from the panel `sweep` defaults to `runs=30`; a real 100-run must go through the CLI (`python -m experimental.sweep --runs 100`) or a direct `POST {"executor":"sweep","runs":100}`. When the user asks to wire a new capability into a UI that lists executors from capabilities, no dashboard.html edit is required — only the dispatch entry + harness runner.
- **PITFALL — validate that every identifier a rule references resolves to a declared input/constant BEFORE generating code.** `_validate_spec` must reject any spec whose `decision_rules_priority` condition names an undeclared symbol (a typo, or an input the spec forgot to list in `required_inputs`). Left unchecked, the compiler emits that identifier as a bare name → the generated module compiles fine then NameErrors at runtime (real case: `same_kind_failures` used in a rule but absent from `required_inputs` → every test failed). The gate exists precisely so a bad spec is refused as INCONCLUSIVE instead of silently shipping a broken prototype. Strip string literals before scanning identifiers, and whitelist Python keywords (`and/or/not/in/is/True/False/None`).
**PITFALL — before wiring a dual-mode chain anywhere, AUDIT that EVERY mode exposes the full trace; one mode's completeness implies nothing about the other.** Mode A (deterministic) traced all 5 individual role contributions and its generated code; Mode B (LLM) originally filled `debate.roles=[]` (only the moderator summary) and the harness did not expose `generated_code` at all — two accountability gaps invisible if you only verified Mode A. The trace-symmetric guarantee to enforce: EVERY run, in EITHER mode, exposes the same seven links — 5 individual role contributions, DECISION_SPEC + `spec_hash`, `generated_code`, `code_files`, the real pytest `verify.command`+verdict, and `mode`/`reproducible`. For an LLM branch, prompt for one `Role: position` line per role and parse them into `debate.roles` (same shape as Mode A), and ALWAYS keep the raw `moderator_output` so a malformed LLM never loses content. PITFALL within that — a trace-completeness test that feeds the data BY HAND (a mock LLM returning per-role lines) proves the ORCHESTRATOR, not the real `llm_debate`; the real gaps above were found only by inspecting what the actual producer fills in, not the simulated one. Lock the guarantee with a test asserting the same 7 links on a real Mode A run AND a simulated Mode B run.
- **Dual-mode (deterministic + LLM) chains must label the LLM branch honestly and put it behind the SAME gate.** Mode B marks `reproducible: false` and, when the backend is unreachable OR the returned spec fails validation, returns `INCONCLUSIVE` with a `reason` — never a fabricated PASS. The LLM spec must pass the identical `_validate_spec` as a deterministic one, so a mode-B spec can't inject an unpatched inconsistency. Import wiring: `LLMClient` lives in `philosophical_council.llm.client` (NOT `code_lab.multiagent`, which only holds `probe_llm`/`resolve_llm_credentials`). A missing backend can hang `probe_llm().get_models()` (no timeout) — bound the whole mode-B call in a `ThreadPoolExecutor` with `fut.result(timeout=90)` (covers the probe AND the chat) so an absent backend returns a clean `LLMUnavailable` → INCONCLUSIVE instead of blocking the harness.
- **PITFALL — a `with ThreadPoolExecutor(...)` context BLOCKS on its hung worker at `__exit__`; never use it around a time-bounded remote call in a LOOP.** The `with` block's exit calls `shutdown(wait=True)`, which waits for the submitted worker — if `_call` is stuck in a backend probe/chat, the timeout from `fut.result(timeout=90)` fires but the `with` exit still blocks forever (a 30-tour multi-run over a down backend would hang the whole sweep, not just one call). Use an explicit pool: `pool = ThreadPoolExecutor(max_workers=1); try: ... fut.result(timeout=90) ... finally: pool.shutdown(wait=False, cancel_futures=True)`. `cancel_futures` needs Python ≥3.9 (this repo is 3.11).
- **`llm_sweep` executor (`experimental/llm_sweep.py`, `kind='llm_sweep'`): a multi-turn LLM experiment that measures CONVERGENCE vs DRIFT across N tours (default 30) of the mode-B chain, then emits a structured synthesis `{observation, conclusion, next_leads}` computed deterministically from the aggregated real traces.** This is the payoff of mode B's non-reproducibility: what a single run cannot tell you, N tours can. It runs the FULL `run_debate_code(mode='llm')` per tour (every tour fully traced: 5 roles, spec_hash, generated_code, real pytest verify), aggregates them, then classifies the run as `HIGH_CONVERGENCE` (all PASS + a single stable spec_hash — the LLM debate reached the same verified contract every tour), `PARTIAL_CONVERGENCE` (some PASS but the spec_hash DRIFTED — drift now measured, not guessed), or `NO_CONVERGENCE` (0/0 compiled — backend down or out of scope; honest, never a fabricated pass). The three-way classifier is the acceptance rule the user wants: is PASS-or-INCONCLUSIVE enough, or must a minimum pass_rate hold before the chain counts as usable. Status in the harness is `passed` only when `n_pass > 0`, else `inconclusive`. Mock-driven: the tours go through `run_debate_b`, so a test can simulate a converged LLM (stable spec), a drifting LLM (vary `required_inputs` per tour — changing ONLY the module name does NOT change the spec_hash, which hashes machine-relevant fields), or a down backend. CLI: `python -m experimental.llm_sweep --turns 30 --task "..."`.
